# Automation Orchestrator (orchestration/)

Runs Red Hat's **Automation Orchestrator** (2026.8) on the demo cluster and
imports two workflows: **Remediate Next Gitlab** — the human-in-the-loop
front door of the CVE remediation loop (lists the open CVE issues in GitLab,
has an LLM pick the next most important one, requires a human to approve the
choice, and posts a `/remediate` comment on the chosen issue, which the
GitLab issue-comment webhook translates into an `agentic-cve-remediation`
PipelineRun) — and **Remediate Test Promote Gitlab**, the full
remediation→test→promotion chain (see below).

This directory holds the workflow definitions and the design notes. The
Kubernetes side — operator, Postgres, the `AutomationOrchestrator` CR, the
worker patches and the workflow import — lives in the gitops app-of-apps as
**`automation/gitops/components/orchestrator`** and installs automatically
with the rest of the demo (RUNBOOK §5). Its setup Job is what re-points the
workflows at a new cluster: it rewrites the GitLab host and project id baked
into the JSONs below, creates the GitLab credential for the HTTP nodes, and
imports + publishes both workflows through the platform's REST API.

## Files

| File | What it is |
| ---- | ---------- |
| `remediate_next_gitlab.json` | Export of the "Remediate Next Gitlab" workflow |
| `remediate_and_promote_gitlab.json` | Export of the "Remediate Test Promote Gitlab" workflow — the full remediation→test→promotion chain (see below) |
| `gen_workflow.py` | Generator for `remediate_and_promote_gitlab.json` — run it in place after editing that workflow; it guarantees the JSON and the embedded python are well-formed |

Both JSONs were exported from the reference cluster
(cluster-b7zgr.dyn.redhatworkshops.io), so they carry that cluster's GitLab
host, project id 1 and credential GUIDs. That is deliberate: the component's
setup Job rewrites exactly those values on import (host, `projects/1/`,
`PROJECT_ID = "1"`, and the two HTTP-node `credential_id`s when it manages
to create a credential), so the committed files stay a faithful export of a
known-working workflow rather than a hand-edited near-copy.
`remediate_and_promote_gitlab.json` is regenerated by `gen_workflow.py`
(that is why it is one long line per node rather than pretty-printed).

## Install

The component chart **`automation/gitops/components/orchestrator`** is the
install path — see its README for the design decisions (why a chart and not
plain YAML, why the setup Job exists, what it does, and the points that
could not be verified against a live platform). On a normal install nothing
in this directory is applied by hand: the app-of-apps installs the operator
and platform, and the setup Job does the rest.

What the setup Job automates, in order (each step is also documented as a
manual fallback in the component README):

1. Waits for the operator to roll out the `automationorchestrator-demo-worker`
   Deployment.
2. Patches the worker: `APP_SCRIPT_NODES_ENABLED=true` (script nodes are
   disabled by default — see below) and the
   `orchestrator-worker-k8s-access` Secret mounted at `/var/run/ao-k8s`
   (the Kubernetes token the workflow scripts use).
3. Discovers the platform's Route, logs in with the generated initial admin
   credentials, and resolves the app project's GitLab id through the
   anonymous API.
4. Clones the gitops repo (the same source Argo pulls), rewrites the
   cluster-specific values in the two JSONs, creates a GitLab credential
   from `scm-auth-secret` (best-effort — see the component README), and
   imports or updates + publishes both workflows.

One step stays manual on every cluster: **the LLM model for the agentic
node** of "Remediate Next Gitlab" (`Select Next Gitlab Issue to Remediate`).
It references a model by GUID, and models are per-instance platform objects
the Job has no way to pick. Open the workflow in the UI and select one
configured in that instance (the demo's AI backend works). The node fails at
run time, not import time, so everything else can be verified first.

## Importing the workflow by hand (fallback)

If the setup Job's import fails (its REST contract has a few unverified
points — see the component README), import through the UI instead: log into
the UI (the Route from
`oc -n automation-orchestrator-operator-system get route`, username
`admin`, password in the `automationorchestrator-demo-initial-admin-password`
Secret), use the import action on the Workflows page, and then re-point two
node settings at THIS instance:

1. **Credentials** — both HTTP nodes (`GET Open Issues from Gitlab`,
   `Comment /remediate on selected Issue`) reference a GitLab credential by
   GUID, which is why their Authentication dropdown comes up empty on a
   fresh instance. Credentials are platform objects, not Kubernetes
   secrets: open the **Credentials** page and create one whose token can
   read issues and post notes on
   `development/spring-boot-example-application` — then select it in both
   nodes. (The token value would be a copy of `scm-auth-secret`'s `token`;
   the remediate-and-promote workflow below deliberately avoids this by
   reading that secret directly instead.)
2. **LLM model** — the agentic node (`Select Next Gitlab Issue to
   Remediate`) references a model by GUID; pick one configured in this
   instance (the demo's AI backend works).

The setup Job's rewrites (GitLab host, project id) must then be applied by
hand too: edit the GET node's URL to this cluster's GitLab and the resolved
project id, and check the script constants in
`remediate_and_promote_gitlab.json` (`GITLAB_HOST`, `PROJECT_ID`).

## The "Remediate Test Promote Gitlab" workflow

`remediate_and_promote_gitlab.json` is the full promotion chain: a human
starts it with an issue number, and the workflow drives everything from the
`/remediate` comment through prod promotion:

1. **Manual trigger** — the runner inputs the issue number (iid).
2. **Build issue notes URL → comment `/remediate`** — same mechanism as the
   other workflow: the `agentic-issue-commands` EventListener picks the
   comment up and starts `agentic-cve-remediation` for the issue.
3. **Wait for remediation, merge and image build** — polls the Kubernetes
   API in-cluster for the issue's remediation run to succeed, then for the
   merge-triggered `ci-build-publish` run (the `ci-build-push`
   EventListener starts it when the remediation MR merges), and takes its
   `IMAGE_URL` / `CHAINS-GIT_COMMIT` / `CHAINS-GIT_URL` results as the new
   image.
4. **Run functional and integration test pipelines** — creates
   `test-image-functional` and `test-image-integration` PipelineRuns against
   the new image (same shape as the hand-run versions: pipeline SA, fresh
   2Gi workspace, `maven-settings`, tests pinned to the built commit,
   evidence comments on the issue). Both must succeed — the first failure
   fails the workflow and blocks promotion.
5. **Promote to prod** — creates a `gitops-cd-prod` PipelineRun with the new
   image and `auto-merge: "true"`, waits for it, and reports the promotion
   MR URL and merge status. The run also passes
   `issue-ref: development/spring-boot-example-application#<iid>` and
   `issue-action: "Closes"` (also gitops-cd-prod's own default): the MR's
   description references the issue with a closing verb, so merging it into
   the gitops repo's default branch **auto-closes the remediation issue** —
   a CVE is only done once the fix ships to prod. (Dev and qa promotions
   reference the issue without closing it; `gitops-bump-image` derives the
   reference from the "Related to #N" line in the MR that landed the
   commit — the app project is public, so the lookup needs no token.) The
   node also posts a closing evidence note on the issue (promotion MR link
   + test PipelineRun names), so the issue carries the whole
   remediation→test→promotion trail even after it closes.

### The worker patches, and why they are needed

Everything in this section is applied by the component's setup Job; it is
kept here because it explains what the workflow scripts actually depend on.

- **Enable script nodes (required — the run fails without this)** — the
  platform ships with script-node execution disabled by default. Every node
  of this workflow after the trigger is a script node, so the first run fails
  at "Build issue notes URL" with `ScriptNodeDisabled: Script node execution
  is not enabled.` (the scripts never execute; the worker refuses the
  activity before running anything). The switch is a platform setting
  (`script_nodes_enabled`, default `false`, Developer Preview) that is read
  from the worker's environment only — there is no CR field or UI toggle for
  it (the `AutomationOrchestrator` CRD has no env passthrough). Enable it on
  the worker deployment (script activities execute in the
  `automationorchestrator-demo-worker` pods):
  ```bash
  oc -n automation-orchestrator-operator-system set env \
    deployment/automationorchestrator-demo-worker APP_SCRIPT_NODES_ENABLED=true
  ```
  The rollout restarts the workers; the setting is cached per process, so the
  restart is what applies it. Manually added env entries survive the
  operator's reconcile (verified in practice), but fields the operator
  itself owns — like `automountServiceAccountToken` — are reset within
  seconds, which is why the token step below also uses a volume/mount.
  Security note from the setting's own docs: script nodes run arbitrary user
  code in the worker process without extra sandboxing, so this is fine for
  the demo cluster but explicitly "not recommended for production
  deployments".
- **Give the worker a Kubernetes token (required)** — getting credentials
  into workflow scripts is a three-way closed door, each verified on this
  cluster: the operator sets `automountServiceAccountToken: false` on the
  worker and **resets any manual flip within seconds** (patching to `true`
  looks like it works, then reverts); script subprocesses get only an
  **allowlisted environment** (locale/PATH vars — the platform's
  `SAFE_ENV_ALLOWLIST` — so env vars added to the worker deployment never
  reach the scripts); and script nodes have no `credential_id` (only
  `http_request` nodes do). What DOES survive the operator's reconcile is a
  manually added **volume/mount** (list fields merge by name/mountPath, like
  extra env entries do). So the token comes from the
  `orchestrator-worker-k8s-access` Secret (created by the component chart: a
  long-lived service-account token for the worker's own SA) mounted into the
  worker at `/var/run/ao-k8s`:
  ```bash
  oc -n automation-orchestrator-operator-system patch deployment \
    automationorchestrator-demo-worker --type merge -p '{
    "spec":{"template":{"spec":{
      "containers":[{"name":"automationorchestrator-demo-worker",
        "volumeMounts":[{"name":"ao-k8s-access","mountPath":"/var/run/ao-k8s","readOnly":true}]}],
      "volumes":[{"name":"ao-k8s-access",
        "secret":{"secretName":"orchestrator-worker-k8s-access"}}]}}}}'
  ```
  (Strategic merge, so re-applying is safe; read the container name from the
  live deployment if the operator renamed it — the setup Job does.)
  The workflow scripts read `/var/run/ao-k8s/token` and
  `/var/run/ao-k8s/ca.crt` (falling back to the projected token paths for
  deployments that do mount them); without the mount the "Comment
  /remediate" node dies with the guard message `found no service-account
  token/CA`. It is the same SA the RBAC scopes, so the credential can
  only create/read PipelineRuns and read one named secret in `tssc-app-ci`.
  Note the mounted files are readable by anything in the worker container —
  on a multi-tenant orchestrator that would expose the token to every
  workflow author; fine here, where the platform has a single author.
- **No platform credential needed** — the `/remediate` comment node is a
  script that reads the GitLab token from the `scm-auth-secret` Secret in
  `tssc-app-ci` (the same single source of truth the pipelines use) through
  the Kubernetes API and posts with a `PRIVATE-TOKEN` header. Nothing to
  copy, nothing to rotate in two places.
- **RBAC** — the script nodes talk to `https://kubernetes.default.svc` with
  their pod's service account. Workflow activities execute in the
  `automationorchestrator-demo-worker` pods (they poll the
  `orchestrator-workflow-queue` Temporal task queue; the background-worker
  handles only internal scheduled jobs), so the component chart binds that
  SA and grants exactly: `pipelineruns get/list/watch/create` in
  `tssc-app-ci`, plus `get` on the single named secret `scm-auth-secret`
  (for the comment node — no list, no other secrets, no other verbs).
  Verify from the cluster:
  ```bash
  oc -n tssc-app-ci auth can-i get secret/scm-auth-secret \
    --as=system:serviceaccount:automation-orchestrator-operator-system:automationorchestrator-demo-worker
  ```
- **Trigger parameter wiring** (verified against the platform): manual
  trigger inputs are declared as a JSON Schema under
  `parameters.input_schema` (the only key `parameters` accepts) and
  referenced downstream as `${trigger.<property>}` — the workflow uses
  `${trigger.issue_iid}`. Two things the publish verifier taught us the
  hard way: every `${...}` sequence anywhere in a script — including in
  *comments* — is resolved and must name an existing node, trigger, or
  property; and references must point at upstream steps only. The first
  script still carries an `isdigit()`-guarded `FALLBACK_ISSUE_IID`
  constant: if the engine ever leaves the trigger expression unsubstituted
  in a script body at runtime, the run uses the constant instead of
  failing.
- **Apply the pipeline change before running this workflow version** — the
  promote node's PipelineRun supplies `gitops-cd-prod`'s `issue-ref` param
  (added in `pipelines/pipelines/gitops-cd-prod.yaml` and forwarded to
  `gitops-bump-image`'s `ISSUE_REF`, which appends it to the MR
  description). A PipelineRun that supplies a param its pipeline does not
  declare fails validation, so re-apply those two YAMLs (or let the sync
  pick them up) before running this workflow version.

### Assumptions worth knowing

- **Build↔issue correlation**: the workflow takes the first
  `ci-build-publish` run that succeeds *after* the issue's remediation run
  finished as the image to test. With one issue in flight (how the demo
  runs) that is exactly the merge-triggered build of that issue's MR; with
  several issues merging concurrently, correlating a build to a specific
  issue would need GitLab API access from the polling script (which has no
  credential injection) — the workflow would need an extra authenticated
  node if that ever matters.
- **In-cluster script execution**: the design assumes workflow script pods
  run on this cluster and can reach `kubernetes.default.svc` with a
  projected SA token. If the orchestrator executes scripts elsewhere, move
  the pipeline-starting steps to `http_request` nodes with an API-token
  credential against the cluster's API URL.
- **Inter-node handoffs are stdout-JSON contracts**: each polling script
  sends all progress output to **stderr** and reserves stdout for a single
  JSON line that the next node `json.loads`es verbatim. (A first version
  printed progress to stdout too; the first run that got past the wait node
  then died in the tests node with `JSONDecodeError: Expecting value`.)
  Relatedly, the wait node snapshots the newest already-failed remediation
  run when it starts: a failure visible in its first moments is a stale run
  from an earlier attempt (the just-posted `/remediate` comment takes a few
  seconds to spawn its PipelineRun), so only a *newer* failed run fails the
  workflow.
- **Timeouts** — two layers, and both matter. The platform kills any script
  node at `settings.timeout` seconds (default **300**) regardless of what the
  script itself would wait — the first version of this workflow died at
  exactly 5 minutes with `Script execution timed out after 300 seconds`
  while polling (Temporal cancels the activity 10 s after that ceiling). So
  the three polling nodes carry explicit `settings.timeout` values sized
  above their scripts' own waits: wait-for-build 11 100 s, tests 5 700 s,
  promotion 2 100 s. The in-script constants (remediation+merge **2 h** — a
  human merges the MR — then build 60 min, tests 90 min, prod promotion
  30 min) fire first, keeping the specific "what was I waiting for" error
  messages.
- The `agentic` LLM node is deliberately absent — no LLM decisions in this
  chain; the human at the trigger is the judgment.
- **The chain is only as good as the issue's decision block**: the workflow
  fails the run — by design, before anything is tested or promoted — when
  the remediation PipelineRun fails, and the most common cause is the
  issue's `FIXED_VERSION` not resolving. It must be a version the
  Artifactory `maven` repo can actually serve: a real Maven Central version
  (verified against Central, not just the advisory) or one of the
  custom-staged `.rhlw-00001` artifacts. Demo-issue examples of exactly
  this: issue 55 advised `tomcat-embed-core 9.0.101` — a version Tomcat
  never published (the 9.0.x line jumps 9.0.100 → 9.0.102) — and issue 18
  advised `11.0.0-M5`, a milestone never published to Central. Fix by
  editing the hidden `<!-- cve-decision ... -->` block in the issue body
  (see pipelines/triggers/agentic-issue-triggers.yaml), or overriding in
  the comment itself (`/remediate` + `FIXED_VERSION: <existing>`).

## Notes

- The CR deliberately omits `spec.imagePullSecrets` (registry.redhat.io
  pulls are covered by the cluster's global pull secret; a dangling ref
  would break pod creation) and `spec.secrets` (the operator auto-generates
  the admin password and encryption key when refs are omitted).
- Cleanup, if you ever want the whole thing gone: delete the Subscription +
  CR first, then the namespace (deleting the namespace alone leaves the
  ClusterServiceVersion orphaned in it):
  ```bash
  oc -n automation-orchestrator-operator-system delete subscription automation-orchestrator-operator
  oc -n automation-orchestrator-operator-system delete automationorchestrator automationorchestrator-demo
  oc delete namespace automation-orchestrator-operator-system
  ```
